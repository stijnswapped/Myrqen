# Held-out evaluation protocol

Recall 1.000 on the corpus a rule was developed against is not evidence that the rule
generalises. It is evidence that the rule fits the corpus. The two are indistinguishable
from inside, which is why this document exists and why the numbers it governs are the
only detection numbers worth quoting to a stranger.

## The freeze

The scanner is frozen at **`5e462345bc969cdf43112036ccfdc6b4061ae162`**.

Measured on the development corpus at that commit: 73 vulnerable and 73 safe cases,
recall 1.000, critical/high recall 1.000, precision 1.000, and zero findings across all
73 safe cases. Both fixture applications at recall 1.0 and precision 1.0. Zero findings
across this repository's own 159 source files and across 3,414 files of unfamiliar
third-party JavaScript and TypeScript.

## The rule that makes the holdout worth anything

**If the scanner changes after a held-out corpus is generated, that corpus is burned.**

Not "reused with a note". Burned. The moment a rule is adjusted in response to a
held-out miss, that corpus has become development data, and every number from it is a
development number wearing a holdout's clothes. A new holdout must be generated by an
author who has not seen the adjustment.

This is recorded here rather than left as an intention because the temptation runs one
way. A holdout that reports 0.6 recall is far more useful than a development corpus that
reports 1.0, and it will not feel that way at the time.

## How a holdout is generated

1. The author has not read `packages/scan` and does not read it during authoring. Not
   the rules, not the taint model, not the tests. A corpus written with the
   implementation in view tests the implementation's own idea of the problem.
2. The author does not read the existing corpus either. Cases written to be *different
   from* the development set are still shaped by it; cases written from the author's own
   sense of how the defect appears in real code are not.
3. The author does not run the scorer while authoring. Every case is judged only by
   "would a competent security reviewer report this".
4. The scorer runs once, at the end, and the result is recorded whatever it says.

## Recording a result

Each holdout run is appended below with its commit, its author's constraints, and its
numbers — including the misses, named. A holdout with no recorded misses either found
none, which is worth stating explicitly, or was not honest.

#### Run 1 is burned — 2026-08-20

The scanner changed in response to what Run 1 found. By the rule at the top of
this document, `benchmark/holdout` is now development data and every number
produced from it after this date is a development number.

What changed, and why it counts as burning the corpus:

* An entry-point adapter layer was added (`packages/scan/src/ast/entrypoints.ts`
  and `packages/scan/src/ast/frameworks/`) so NestJS controllers, SvelteKit
  endpoints, Nitro routes, Lambda and Worker handlers, Electron IPC channels,
  queue processors and CLI commands produce entry points and seed the taint
  model. The architectures it teaches the engine were chosen by reading Run 1's
  misses.
* Individual rules were generalised against named held-out cases.

The first change would arguably have happened anyway — those are the
architectures developers use, not the architectures this corpus happens to
contain — but the *order* was miss-driven, and a corpus is burned by the
sequence, not by the intent.

`benchmark/holdout` is therefore promoted to development status. Its numbers are
still reported, and they are still more informative than the development
corpus's, but they are no longer a held-out result and must never be quoted as
one. A new corpus is required before any generalisation claim is made again, and
its author must not have read `packages/scan` or this document's Run 1 section.

The families were chosen to avoid every architecture the engine already had an

harder and fairer question than Run 1 asked.

```
holdout-2: 76 case(s) — 11 vulnerable, 11 safe, 54 in an unparsed language
recall                0.091 (1/11)
critical/high recall  0.091 (1/11)
precision             0.500
safe-case FP rate     0.091 (1/11 safe case(s) produced a finding)
```

54 of the 76 cases are Python, Java, Ruby, or Go, which the engine does not parse
and which are excluded from the score rather than counted as misses. The scored
population is therefore 11 vulnerable and 11 safe cases, almost all from
`modern-js`. A ratio out of eleven is a weak estimate and is quoted here with
that caveat attached, not without it.

Detected: one case. Missed: ten. One safe case produced a finding
(`h2-modern-js-incident-stream-origin`, `perimeter-cors`).

**Ten of the eleven produced no candidate at all** — not a wrong line, not a wrong
class, nothing. `benchmark/explain.mjs --corpus benchmark/holdout-2` gives the
same reason for each: no entry point is recognised, so no binding is
caller-controlled, so every data-flow rule in the engine stays silent. It is
precisely the failure Run 1 diagnosed, in architectures Run 1 did not contain.

The conclusion is structural and worth stating plainly, because it is the most
useful thing either run has produced:

> The entry-point adapter layer works — it took Run 1 from 0.148 to 1.000. But
> its coverage is strictly per-architecture. An application built on a framework
> with no adapter is very nearly invisible to this engine, and the engine does
> not currently say so.

Two things follow. Adapters are needed for Deno, Bun, Astro, TanStack/SolidStart
server functions, WebSocket and SSE handlers, and extension service workers. And
independently of that: a scan that recognises no entry point in a file should say
so in its coverage output, loudly, rather than reporting no findings and letting
silence read as safety.

One change *was* made after reading this run, and the reasoning for why it does
not burn the corpus is recorded here rather than assumed. `packages/scan/src/index.ts`
now adds a coverage line when a parsed file yields no entry point, naming the
count and the frameworks it did recognise, and saying outright that a clean
result is unproven when most of the project was not understood. That line is a
*coverage note*, not a candidate. Recall, precision and the false-positive rate
are computed from candidates alone, and the scores above were re-measured after
the change and are byte-identical. A change that cannot move the metric cannot
tune against it.

**No rule and no adapter was changed in response to this run, so this corpus is
not burned.** It remains the only clean measurement of generalisation this
project has, and the next person to work on detection should keep it that way
until they are ready to spend it.

##### How it was authored

Six families, 34 vulnerable and 34 safe cases, 16 distinct classes, every case
JavaScript or TypeScript — which is why the scored population is 68 rather than
the 22 Run 2 managed out of 76.

The application source was written earlier by blind authors, one family each. The
ground truth was written in one pass by a **single subagent whose prompt carried
the corpus specification and nothing about the implementation**, which is what
made its blindness structural rather than a matter of self-restraint. Its
constraints, confirmed in its own report: `packages/scan/` was never opened,
listed, or grepped; `benchmark/corpus/README.md` was the only file read in any
other corpus; `benchmark/holdout/` and `benchmark/holdout-2/` were never touched;
`DETECTION-PLAN.md`, `DETECTION-BASELINE.md` and this document were never read;
no scanner, scorer, benchmark, build or test was run. No source file was edited —
every recorded line was read off disk and re-verified against the file's own line
count.

`build-corpus-manifest.mjs --corpus benchmark/holdout-3` found **zero** problems.

Two authoring decisions shape what the run can measure, and both were the right
call:

* **Routes were omitted wherever the route is not declared in the case file.**
  Twenty-two of the 34 vulnerable cases carry no `route`, because the scorer scans
  each case alone and a route declared in an absent router can never be
  attributed. An omitted route is not scored; a wrong one would have manufactured
  misses. This is the check Run 2's post-mortem asked for, applied.
* **Twenty of `realtime-desk`'s thirty files are deliberately unlabelled** —
  database helpers, loggers, serialisers, type modules. They contain no defect,
  but they are plumbing rather than near-misses of a vulnerable form, so labelling
  them safe would have added false-positive surface without testing anything.

##### What this run establishes

Run 2 said the engine is blind without an entry point. Run 3 says the adapter
layer fixed that — 68 cases produced candidates across all six architectures, and

#### Run 3 is burned — 2026-08-21

The scanner changed in response to what Run 3 found, so by the rule at the top of
this document `benchmark/holdout-3` is now development data. Every number below
is a development number. **Only the Run 3 figures above may be quoted as a
held-out result, and they are 0.294 recall.**

Four changes were made, all of them precision-first, and each has a paired
regression test that asserts the correctly written form is silent *and* that its
defective sibling is still found — because a guard with no paired test is
indistinguishable from a rule switch.

* **A containment check written with `relative()` is now a guard.**
  `relative(base, candidate)` tested for `..` and `isAbsolute` is the idiom the
  documentation recommends over prefix matching, precisely because
  `resolved.startsWith("/srv/previews")` also accepts `/srv/previews-old`. The
  engine knew only the weaker form, so it reported the better-written of the two
  handlers. Also recognised when the test lives in a named predicate in the same
  file, which is where real code puts it.
* **A validating helper still counts through `toString()` and a conditional.**
  `const target = raw ? previewTarget(raw) : null; fetch(target.toString())` — the
  SSRF rule already read producing helpers, but stopped at the render and at the
  ternary, so the handler that parses the URL and checks its host against a closed
  set was reported and the one that fetches the raw string was not.
* **A CORS origin predicate anchored at a label boundary now gates the
  reflection.** Credentialed CORS over per-customer subdomains has no fixed list
  to be a member of, so the membership test the rule understood was unavailable.
  The label boundary is required rather than inferred: an unanchored
  `endsWith("pulse.dev")` still reports, because it accepts `notpulse.dev`.
* **A fluent query-builder chain is now recognised as a record lookup.**
  `db.select().from(orders).where(eq(orders.id, params.id)).limit(1)` contains no
  method name the object-ownership rule knew — the table arrives through `.from`,
  the filter through `.where`, and the terminal link is whichever modifier was
  written last. Keying on the terminal name switched the rule off for Drizzle and
  Kysely, which is most of the TypeScript ORM population, and for the commonest
  form the defect takes.

##### What a fourth corpus has to answer

**A ruling on path-parameter notation, made before scoring.** Added 2026-08-24. The
engine reports a file-routed parameter as the file spells it and an Express parameter

this the moment their rule gaps close, so it is not hypothetical.

#### Run 4 is burned — 2026-08-24

By the rule at the top of this document, and by sequence rather than intent. Four

##### What changed, and what it moved

Four adapters, for architectures with no coverage at all: **AdonisJS v6** controllers
and middleware, **Convex** functions, **Hapi 17-21** routes and prerequisites, and
**Effect / @effect/platform** routers. Plus the three engine changes each of them
turned out to require:

* **`yield*` is now unwrapped wherever `await` is.** The engine handled one and not
  the other, so an Effect handler — where every read of the request is a `yield*` —
  lost its taint at the first statement. True of any generator-based code, so the fix
  is in the taint model rather than in the adapter.
* **`db.rawQuery` is a SQL sink.** The list carried `raw` and Prisma's `queryRaw`;

  statement had no SQL sink at all.
* **An allowlist in a conditional expression is a guard.**
  `ALLOWED.has(asked) ? asked : "default"` is how a sort column is vetted in real
  code, and the guard pass could only see a membership test inside an `if` whose
  failing branch terminates. This one is a **precision** fix, and it closed a false
  positive on Run 4's own safe half.

##### Two performance lessons, both from the gate

* **A lookbehind cost more than half the scan.** Keeping Hapi's `{noteId}` while still

  `pnpm benchmark:performance` caught it within minutes of it being written, which is
  the entire argument for having that gate.
* **Memoizing the taint analysis is worse, twice measured.** `analyzeFunction` runs from

  **34% slower** (3,486 ms to 4,669 ms), because cloning the scope costs more than
  recomputing it. Reverted permanently. **Do not try this a third time.**

### Rulings for Run 4 — 2026-08-24, before the corpus exists

Recorded before a line of `holdout-4` is written, because a rule settled after
seeing a score is indistinguishable from moving the goalposts. Both questions come
from Run 3's post-mortem, which asked for exactly this.

**R1 · Line attribution.** The corpus states a `lineRange` wide enough to span the
composition *and* the sink. Four of Run 3's cases turned on a disagreement about
which of the two a reviewer would comment on, and neither answer was wrong. The
engine's rule is settled and is "report where the fix goes"; the corpus's job is to
accommodate it rather than to guess it. An author who cannot decide should widen the
range, not narrow it.

**R2 · Route notation.** A case states the route **as the framework declares it in
the file** — `:id` where the framework spells `:id`, `[id]` where it spells `[id]`,
`$id` where it spells `$id`. No normalisation, on either side.

This is the ruling rather than the alternative, and the reasoning is worth keeping.
The engine reports the address as the file declares it, which means it emits two
notations for one concept — `:orderId` for Express, `[id]` for file-based routing.
That reads like an obvious thing to normalise until it is measured: Run 3's own
ground truth is *internally inconsistent* here, asking for `[id]` from its Astro
cases and `:id` from its Deno and TanStack ones for handlers the engine spells
`[id]` and `$supplierId`. Normalising the engine to `:id` would have broken two
cases that pass and gained nothing. So the notation follows the framework, the
corpus author reads it off the file they are writing, and neither side guesses.

**R3 · Novel classes are permitted and wanted.** All three previous holdouts
introduced **zero** vulnerability classes the development corpus did not already
contain, so the engine's taxonomy has never itself been held out — and unmodelled
classes are half of Run 3's remaining loss. Run 4's authors are given no list of
categories. They name the defect they see, in `snake_case`, whether or not this
engine has a rule for it. A class with no rule is the most useful thing a holdout
can contain.

**R4 · Route reachability is fatal.** `build-corpus-manifest.mjs` now fails rather
than warns when a declared route appears in neither the case file, its own path, nor
its `extraFiles`. Run 3 carries four such cases and one of them can only ever score
as a miss; Run 4 will carry none.

**R5 · `outOfScope: "cross_module"` may be marked while writing, and is expected to
be rare.** The mechanism exists and Run 4's authors may use it — but the finding
that motivated it has been retracted. Bisecting Run 3's misses put cross-module data
flow at the primary cause of **none** of them, so an author who reaches for this
field should be describing a flow that genuinely leaves the file, not a case that
merely looks hard.

**The target, stated now.** Static recall **0.62–0.70** with cross-module excluded
and reported separately, precision ≥ 0.90 and safe-case false positives ≤ 0.03 held.
The gate numbers themselves do not move. If Run 4 lands below the target that is the
measurement, and it gets recorded whatever it says.

#### Run 3, after the guard work — 2026-08-24

Recall unchanged at **0.471**, precision 1.000 and safe-case false positives 0.000 on

Three engine changes:

* **An HTML escaper is recognised by its body rather than its name.** The same

* **An anchored regular expression is a guard.** `if (!/^\d{4}-\d{2}$/.test(period)) return`

  testing `url.pathname` disarmed `url` and lost the fixture's own path traversal

  now clears the tested path and nothing else.
* **`dom_html_injection` — a new class.** `innerHTML`, `outerHTML`,

  specification and the sixteen fixtures are hand-written.

to the same latent defect: **the return value of a local authentication helper is
treated as caller-controlled**, so `requireServiceToken(request).tenantId` used as a
path segment reads as attacker-controlled when it is server-established identity. The
sink is correct and the taint model is not ready for it. Buying one case for two
false positives is the trade this project's history says not to make, so the sink
waits for the identity work rather than shipping ahead of it.

## The scope decision — 2026-08-21, before Run 4 exists

Taken deliberately, in writing, and **before** the corpus it will judge is
written. That ordering is the whole of its legitimacy: choosing a target after
seeing a score is indistinguishable from moving the goalposts, which is the move
this document exists to prevent.

### What was wrong with the old target

Two sets of numbers were in circulation. The stricter — critical/high recall
≥ 0.97, overall ≥ 0.93, precision ≥ 0.95, safe-decoy false positives ≤ 0.02 — was
attributed to `MASTER-BUILD-PROMPT.md`, which names no number at all and only asks
for a benchmark that *measures* recall and the false-positive rate. The enforced
one was `benchmark/score-corpus.mjs`'s own 0.95 / 0.90 / 0.90 / 0.03.

Neither was reachable, and not because the rules are weak. `benchmark/score-corpus.mjs`
scans each case **alone**, in an empty directory, with **no agent involved**. It
measures the static pass. The product is the host agent *plus* the static pass, and
the static pass deliberately does not follow data across module boundaries — the
architecture gives that to the agent, and the engine states the limitation in its
own coverage output on every scan.

The ceiling arithmetic in `DETECTION-PLAN.md` makes the consequence concrete: of
holdout-3's 34 vulnerable cases, six are cross-module. Everything else, done
perfectly, reaches about 0.765. So the gate could only be met by building a
capability the product says it does not have — or by never meeting it and calling
that failure.

### The decision: name the pitch, do not move the goalposts

**The gate numbers do not change.** What changes is which cases they are computed
over. A case may be marked `outOfScope: "cross_module"` by its author, and those
cases are scored **separately, with their own recall figure**, exactly as cases in
languages the engine cannot parse already are.

This is not a new principle. `score-corpus.mjs` has always held that "a language
the engine cannot parse is a limitation, not a miss". *A flow the engine does not
follow* is the same sentence about the same kind of boundary. The alternative —
lowering 0.90 to something the static pass can reach — would have hidden a
deliberate architectural boundary inside an arbitrary number, and left nobody able
to say how large it is.

Guards, because this field is the one an author could use to make a number look
better, all enforced by `benchmark/build-corpus-manifest.mjs` and covered by
`tests/corpus-scoring.test.mjs`:

* only a reason the scorer knows is accepted — a typo fails the merge rather than
  silently excluding or silently counting a case;
* only a **vulnerable** case may carry it, since a safe case has nothing to be out
  of scope about;
* the `why` must argue the boundary — name the module the value arrives from — so a
  reader can disagree with the claim rather than take it;
* the excluded cases are **reported with their own recall**, because a limitation
  nobody can see the size of is a limitation nobody ever decides to remove.

### `benchmark/holdout-3` is deliberately not relabelled

Not one of its cases has been marked. Six of them are cross-module and would
qualify, and marking them would raise its recall from 0.441 to roughly 0.54 — which
is exactly why it has not been done. Labelling a case after watching it fail is
the forbidden move whatever the field is called, and holdout-3's numbers stay as
they were scored.

The mechanism applies from **Run 4** onward, to an author who marks cases while
writing them, from the code, without having run anything.

### The second gate, which nothing can measure yet

The static pass is one half of the product. The other half is the host agent, and
no harness scores it against a corpus: the cases are isolated files with no
application to exercise, and `benchmark/analyzer.mjs` — the deterministic
stand-in — needs a running application to probe.

What does exist is `node benchmark/run.mjs`, which drives the whole product path
against `fixtures/vuln-shop` and `fixtures/safe-app`: static pass, agent
validation, dedupe, report. It reports recall 1.000 with 9 of 14 findings verified
— on fixtures the rules were developed against, so it carries the same caveat the
development corpus does and proves nothing about generalisation.

**So there are two measurements, they answer different questions, and neither
answers the other's.** Both belong in any statement about detection:

| | what it measures | what it cannot say |
|---|---|---|
| `score-corpus.mjs` | the static pass, per case, in isolation, no agent | what the agent adds |
| `benchmark/run.mjs` | the whole product path on two fixture applications | anything about generalisation |

Building a harness that scores the agent's contribution on a held-out corpus is
open work, and it is the prerequisite for any whole-product recall claim. Until it
exists, the honest sentence is the long one: *the static pass detects X of what a
corpus nobody tuned against contains, cross-module flow excluded and reported
separately, and what the agent adds on top has not been measured.*


## Run 5

### Rulings for Run 5 — 2026-08-24, before the corpus exists

Recorded before a line of `holdout-5` is written. Run 4 is the reason this section is
longer than Run 4's: a ruling of mine destroyed that measurement, and the repair
belongs in the rulings rather than in the post-mortem.

**S1 · R1, R2 and R4 carry forward unchanged.** Line ranges span composition and
sink and are widened when the author is unsure; routes are stated as the framework
declares them, with no normalisation on either side; a declared route that appears in
neither the case file, its own path, nor its `extraFiles` fails the build. All three
worked in Run 4 and none of them is what went wrong.

**S2 · R3 stands, and the join changes.** Novel classes are still permitted and still
wanted — the engine's taxonomy has never been held out, and a defect class with no
rule remains the most useful thing a holdout can contain. What failed in Run 4 was
not the freedom, it was what I did with the result: five blind authors invented thirty
class names, the scorer compared them to the engine's by **exact string equality**,
and the run scored 0.033 while class-blind recall on the same corpus was 0.433. That
measured naming.

So an author now states **both**:

- `category` — the defect's name in `snake_case`, invented freely, as in Run 4.
- `cwe` — the closest single CWE identifier, e.g. `CWE-639`.

CWE is the join because it is **external**. Handing authors this engine's own rule
categories would tell them what it detects and they would write to the list, which is
the leakage §0 forbids; CWE is a public standard that predates this project, the
engine already emits it on every candidate (`taxonomy: ["CWE-89", "OWASP-A03"]`), and
neither side has to guess the other's vocabulary. An author who believes no CWE fits
says so in `cweNote` and the case is scored class-blind only, which is a smaller loss
than a wrong join.

**S3 · Three recalls are reported, and the primary one is named in advance.**

| Figure | What it measures |
|---|---|
| **`cweRecall`** — **the headline** | A candidate in range whose taxonomy contains the case's CWE. Detection *and* correct classification. |
| `classBlindRecall` | A candidate of any class in range. The detection ceiling — what the engine saw at all. |
| `exactClassRecall` | String equality on the invented name. Diagnostic only; it is expected to be low and a low value means nothing on its own. |

Naming the headline before the corpus exists is the whole point. Run 4's headline was
chosen after the fact from three candidates, and whichever I had picked would have
been arguable.

**S4 · A gap between the three is a diagnosis, not a licence to relabel.** If
`classBlindRecall` far exceeds `cweRecall`, the engine is finding the defect and
classifying it differently from the author — a taxonomy problem, and the fix is to
argue it case by case in this document, in public, **after** the score is recorded.
If both are low, it is a detection problem. Ground-truth labels are not edited to
close either gap; §0 forbids it and Run 4 was left at 0.033 rather than retro-labelled
for exactly this reason.

**S5 · Scored once, then burned.** The corpus is scored a single time against the
engine as it stands at the recorded commit, and the number is written down before any
fix is contemplated. The moment the scanner changes in response, `holdout-5` is
development data and every later figure from it is labelled as such.

**S6 · Authors are blind, and the blindness is the instrument.** No author reads
`packages/scan/**`, any existing corpus, `docs/12-release/**`, `docs/internal/**`, or
any `*last-run*` / `*baseline*` file, and no author runs a build, test, scanner or
linter. A corpus written with the implementation in view tests the implementation's
own idea of the problem.

**S7 · What Run 5 is not allowed to do.** It may not be re-authored, re-scored,
partially discarded, or have families dropped after the score is seen. If a family
turns out to be unusable for a mechanical reason — a validator failure, a corrupt
case — that is recorded here with the reason and the family is excluded *from both
numerator and denominator*, before the score is read, or not at all.

### What hypothesis 3 actually was

`prisma.ticket.findUnique(...)` in `ticketing-elysia` was declined for two reasons, neither
of them the return:

```ts
const recipient = await prisma.account.upsert({ where: { email: body.recipientEmail } })
if (recipient.id === ticket.ownerId) return status(409, { error: 'already_owned_by_recipient' })
```

That reads as an ownership comparison — an owner column, an equality, an early return —
and it is a duplicate-transfer check. `recipient` is fetched by an address out of the
request body, so the caller chooses both sides and it can never fail for the ticket they
are stealing. `classify` correctly calls a row the store handed back "server", because an
id fetched under an ownership predicate and reused is the *correct* two-step pattern; what
was missing is that the comparison must be against **the identity**, which is what this
rule's own description always said.

And the row never reached the response, because it was not meant to:

```ts
await prisma.ticket.update({ where: { id: ticket.id }, data: { ownerId: recipient.id } })
```

The read is the authorization decision — it fixes which row the write lands on. The rule
had two escape routes, "the row is returned" and "the lookup itself mutates", and a
separate read and write is neither.

### The bug that hid a whole class

`missing-handler-authentication` threw on a webhook reported without a verified sibling:
`contrast[0]!.label` on an empty array. The rule's own `try`/`catch` recorded it in
`coverage.parseFailures` and the scan completed, so the case read as a **clean miss** and
every figure was computed as though the rule had looked and found nothing.

Silence caused by an exception is not the same measurement as silence caused by a rule
declining, and the two cannot be told apart after the fact. `score-corpus.mjs` now fails
the run on any rule exception, unconditionally and with no ratchet — there is no
acceptable number of these. An audit across all seven corpora found this one and no other.

## Ruling U7 — every figure carries its interval, and the comparison is fixed in advance

Added 2026-08-25, after computing something that should have been computed before Run 5.

Every recall and false-positive figure in this document is a binomial proportion over
about thirty trials. None had ever been published with its uncertainty. Computed:

| Blind run | `cweRecall` | 95% interval |
|---|---|---|
| Run 5 (corrected) | 0.300 (9/30) | [0.167, 0.479] |
| Run 6 | 0.333 (10/30) | [0.192, 0.512] |
| Run 7 | 0.250 (8/32) | [0.133, 0.421] |

| Blind run | safe-case FP | 95% interval |
|---|---|---|
| Run 5 | 0.267 (8/30) | [0.142, 0.444] |
| Run 6 | 0.069 (2/29) | [0.019, 0.220] |
| Run 7 | 0.125 (4/32) | [0.050, 0.281] |

**Earliest comparable run against latest: recall p = 0.66, false positives p = 0.16.
Neither is distinguishable.** On thirty cases a difference below about 0.35 is not
measurable at all. Detecting a true five-point improvement at this precision needs roughly
1,400 cases; ten points needs 330.

### What this retracts

Two claims in this document, both made by the people who own the numbers:

1. **"The recall work did not generalise"** (Run 6, restated after Run 7). Not supported.
   The three comparable blind figures are flat within noise. The supportable claim is
   weaker and worse: *the measurement has never been able to resolve the changes the work
   produces.*
2. **"The precision work generalised"** (Run 6, and repeated in the Run 7 write-up as
   "p = 0.043, and that one is real"). Not supported either. That p-value compares Run 5
   with Run 6 — a pair chosen after seeing the numbers. With three runs there are three
   pairs, and testing until one clears 0.05 is the reporting-layer version of the mistake
   §0 exists to prevent. Earliest against latest is p = 0.16.

The false-positive work may well be real. Seven rounds of it moved the development corpora
a long way and there is a mechanism for every fix. But *this corpus programme has not
demonstrated it*, and the difference between those two statements is the whole point of
running blind at all.

### The rule

- **No proportion is published without its 95% Wilson interval.** `score-corpus.mjs`
  computes them, writes them into `totals.intervals`, and prints them beside every figure.
  The generated summary carries them, and `verify-docs.mjs` treats an interval bound as a
  legal figure so the honest form is the easy one.
- **The comparison is earliest comparable blind run against latest**, computed in
  `scripts/generate-benchmark-summary.mjs`, not chosen after the fact.
- **The floors stay point-estimate ratchets.** A ratchet that waits for significance lets a
  real regression through for as long as it hides inside the noise. What changed is that a
  floor breach now prints whether it is distinguishable, so a reader knows what to conclude.
- **Run 4 is excluded from the series.** It scored exact class-name agreement, which its own
  write-up diagnosed as measuring the wrong thing. Averaging it in would be the same error
  in the other direction.

### What follows, and it is not another detection phase

The bottleneck is the instrument. Thirty-case single-use corpora cannot see the effects
this work produces, so the next thing to build is a measurement with enough n to resolve
them — real-world vulnerability data at scale, hash-partitioned into development and
held-out by construction so the holdout cannot be tuned against. Availability and
licensing to be verified before anything is built on it.

**Verified, 2026-08-27** — `docs/internal/advisory-corpus-yield.md`. The npm half of the
GitHub Advisory Database yields an estimated 428 to 1740 localizable cases (51.5% of
advisories carry a resolvable fix commit, 50% of those localize to ≤3 files and ≤60 changed
lines; both bounds compounded). That moves the resolution from 0.346 to between 0.095 and
0.062. A single 100-vulnerability sample already contains 51 distinct CWEs against 31 in the
whole hand-authored reference corpus.

The constraint is licensing, not availability: the advisory data is CC-BY-4.0 but the code
is under each repository's own licence, and 3 of 8 sampled repositories are copyleft or
declare nothing. The design that avoids the question is to store references — repo, commit,
path, line range, CWE — and fetch at benchmark time, which also satisfies §16 by
construction. A case that cannot be fetched reads as `unavailable` and leaves every
denominator, the same rule that already governs an unmeasured agent run.

Still unmeasured, and it is the assumption the whole corpus rests on: **a fix commit shows
where the fix went, not where the defect was.** Whether the pre-fix line is derivable from
the diff at a useful rate needs a hand-check on ~30 cases before anything is built.

Second, and independent of corpus size: `endToEnd.recall` is still `null`. The product's
differentiator — agent verification against a running application under two identities — is
in no number published anywhere, while seven rounds of work went into the half a competitor
could copy. Whether static-pass recall is even the right target is unmeasured.

## Ruling U8 — the agent arm was measured with the skill installed, and is retracted

The first agent measurement this project produced is withdrawn. It was labelled
`agent-alone`, meaning a generic coding agent with no Myrqen skill, no static findings
and no methodology — the baseline a skill arm would later have to beat. It was not that.

### What happened

`benchmark/score-agent.mjs` spawned `opencode` with `HOME: process.env.HOME`. Two
directories on the development machine hold the Myrqen skill, both written by the CLI's own
installer:

- `~/.config/opencode/skills/myrqen`
- `~/.claude/skills/myrqen`

Both are dated 2026-08-20, before any agent run. opencode advertises every skill it
discovers under those roots in the model's system prompt. The arm named "no skill" was
therefore handed the skill by the host.

### The evidence

Asked to list its available skills, the same model on the same case directory answers
differently by environment alone:

| Environment | Skills advertised |
|---|---|
| `HOME` = the operator's | ~40, including `use-railway` — the sibling of `myrqen` in `~/.config/opencode/skills/` |
| `HOME` = a per-run sandbox | 1, opencode's own `customize-opencode` |

`use-railway` and `myrqen` are the only two entries in that directory. A listing containing
one was a listing of a directory containing both.

### Why it is retracted rather than corrected

The run cache stored `status`, `findings` and `safety` — not the transcript. So it cannot
be established, run by run, whether the skill was actually read. The figures are therefore
**unsettled, not disproven**, and §0 does not permit an unsettled figure to stand as a
result. The affected numbers, all now marked `retracted` in their run files with the
figures preserved under `retractedFigures`:

- `agent-reference-last-run.json` — `hy3-free`, 12 measured vulnerable cases
- `agent-reference-dev-last-run.json` — `nemotron-3.5-lightning-free`, 11 measured
- `agent-vuln-shop-last-run.json` — `hy3-free`, the fixture arm

The claims withdrawn are class-blind recall 1.000 on two independent models, and a
safe-case false-positive rate of 1.000 on both. Neither the recall nor the false-positive
figure reached a public surface: `endToEnd.recall` in the generated summary was `null`
throughout and remains so. Nothing needs correcting outside this repository.

The run cache was burned, which is the same rule the corpora follow: if the conditions under
which a figure was generated are compromised, the figure is burned rather than reinterpreted.

### Two failures that look identical to a null result

Found while fixing the above, both worth recording because each makes a working agent
indistinguishable from an agent that found nothing:

1. **Path transcription.** macOS puts `os.tmpdir()` at a fifty-character random path. A
   small model reproduced `.../00000gn/T/probe-KMzxNx` as `.../00000gn_T/probe-KMzxNx`, and
   every file read failed. This scores a model on copying a path rather than on finding a
   defect, and it penalises hardest the weaker models whose ceiling is the thing being
   measured. Case directories now sit at a short root; contents are unchanged.
2. **A capability floor, not a quota.** `opencode/nemotron-3.5-lightning-free` answers a
   one-word prompt, then reads `.` and gives up on the real task. Recorded so a weak model
   is not mistaken for a rate limit — the distinction this harness exists to draw.

### The rule

- **An agent arm states the environment it was measured in, or it states nothing.** Every
  run gets an empty `HOME` and an empty `XDG_CONFIG_HOME`. `XDG_DATA_HOME` stays real
  because the provider credential lives there and a scrubbed one cannot authenticate; it
  holds no skills.
- **The arms differ by one line.** `--arm skill` copies the portable skill into the case
  directory and says where it is. Same model, same cases, same answer contract, same
  scorer, separate cache keys and run files. The difference between arms is the skill and
  nothing else.
- **Asserted in tests, not in review.** `tests/agent-harness.test.mjs` fails if the spawn
  environment passes `process.env.HOME`, and fails if a case path grows long enough to be
  mis-transcribed. Both failures are invisible in an aggregate, which is why neither is left
  to a reader's attention.
- **The re-measurement is paired.** Same case, both arms, back to back, so any prefix of an
  interrupted sweep is a valid comparison. At n ≈ 15 a paired test resolves a difference
  that two independent proportions cannot — which is ruling U7 applied to this arm rather
  than relearned on it.

### Status

Not yet re-measured. Every free model on the account refuses the real prompt: a one-word
probe succeeds on `nemotron-3-ultra-free` and the actual task is refused immediately, so the
limit is context-sized rather than per-request. `endToEnd.recall` stays `null`, and the
honest statement of what this project knows about its agent half is: nothing yet.

## Ruling U9 — the agent half, measured for the first time

Run 2026-08-28. The first agent figure this project has produced that is not retracted:
38 of 38 cases measured, **zero provider failures**, so nothing is excluded from any
denominator and no unmeasured case is standing in for a miss.

- **Arm:** `alone` — a generic coding agent, no Myrqen skill, no static findings, no
  methodology. Environment sandboxed per ruling U8, so the host's installed skill is not
  discoverable.
- **Model:** `opencode/nemotron-3-ultra-free`. A free tier, and therefore a **floor** rather
  than a claim about what a frontier agent does.
- **Corpus:** `benchmark/reference` dev half — 19 vulnerable, 19 correct files.

### The figures

Both instruments ran the same 38 case directories, byte-identical, scored by the same
matcher. That makes the comparison **paired**, so McNemar is the correct test and it uses only
the cases where the two disagreed.

| | static pass | agent alone |
|---|---|---|
| class-blind recall | 0.158 (3/19) [0.055, 0.376] | **0.895 (17/19)** [0.686, 0.971] |
| CWE-matched | 0.158 (3/19) | 0.684 (13/19) |
| false positives on correct files | **0.000 (0/19)** [0.000, 0.168] | 0.895 (17/19) [0.686, 0.971] |

**Detection**: both 3, agent only 14, static only 0, neither 2. McNemar **p = 0.0001**.
**False positives**: both 0, agent only 17, static only 0, neither 2. McNemar **p < 0.0001**.

Two results, both distinguishable, pointing opposite ways. The agent found every case the
static pass found and fourteen more, and there is not a single case the static pass caught and
the agent missed. It also flagged seventeen of nineteen correct files.

### What this settles

**Run 7's diagnosis was right and its remedy was in the wrong half.** Recall split 0.875/0.042
by whether the sink was a language primitive or a framework's own vocabulary, and the
conclusion was that a model already knows the vocabularies. Measured: it does. Fourteen cases
the engine could not see, after seven rounds of rule work, the agent saw with no help at all.

**Recall is not the product's problem. Precision is, and it belongs to the agent.** A scanner
that reports on 17 of 19 correct files is unusable at any recall. The engine's contribution is
now legible for the first time: it is the half that stays quiet.

### What it does not settle, and the labels that travel with the number

- **The model is a floor.** A free tier says nothing about a frontier agent, in either
  direction — a stronger model may well be both more thorough and more disciplined.
- **The arm is not the product.** "Agent alone" has no skill, no static candidates and no
  methodology. It is the baseline the skill has to beat, and the skill arm is the run that
  matters for the product.
- **The static column's false-positive rate is partly tuned.** D27 and D28 were fixed against
  a dev-half case on the same day, moving it 0.053 to 0.000. The holdout half, untouched,
  reads 0.167 (2/12). The agent column has no such exposure — nothing about the agent was
  tuned against anything.
- **Nineteen cases resolve nothing under 0.45.** These two gaps are far larger than that,
  which is why they read at all; a smaller effect on this corpus would still be invisible.

### The consequence for what gets built

`endToEnd.recall` stays `null` in the generated summary until the skill arm runs, because
"agent alone" is not the product and publishing it as one would be the U8 mistake in a new
form. What this changes is priority: further static rule work buys recall the agent already
has, while the precision problem — the one the challenge pass in
`packages/skill/myrqen/references/METHODOLOGY.md` was written for — is now measurable and
untested.

## Ruling U11 — one sentence moved precision; the whole skill did not

Run 2026-09-02 on Claude Code, the agent the product actually ships against. Three arms, same
10 correct files from the reference dev half, paired.

Safe cases only. A false positive is a finding on a correct file, so vulnerable cases answer
nothing here and omitting them halves a sweep — which mattered, because the budget was the
operator's own token allowance.

| arm | false positives | findings |
|---|---|---|
| alone | 1.000 (10/10) | 39 |
| alone + the portable skill | 1.000 (10/10) | 39 |
| alone + one sentence | **0.571 (4/7)** | **7, against 28 on the same 7** |

The sentence, and nothing else changed:

> Most files in a codebase are correct. Report only what you would file as a defect for
> someone to fix, and write an empty array if there is nothing worth filing.

**Skill against alone**: zero discordant pairs, identical volume, McNemar p = 1. Not a weak
effect — no effect on any metric measured.

**Threshold against alone**: fewer findings on **7 of 7** cases and more on none, sign test
**p = 0.0156, distinguishable**. Three of seven correct files came back completely clean, the
first empty arrays any arm has produced. The binary false-positive rate gives McNemar p = 0.25
on 3 discordant pairs, so *that* metric is not yet resolved; the volume result is.

### Why this is the important result

Capability was not the constraint and neither was instruction volume. `nemotron-3-ultra-free`
alone flagged 0.895 of correct files; Claude Code alone flagged 1.000. **More capable model,
slightly worse precision.** Then 36KB of skill across five files — including the challenge
pass, written precisely for this — moved nothing, and one sentence moved reported volume by
75%.

The agent was doing what it was asked. "Review this for security vulnerabilities" against a
correct file has no good answer except to find something arguable, and nothing in the contract
had ever said that finding nothing is a valid answer. The challenge pass cannot fix that
because it runs *after* candidates exist and only asks the agent to re-examine its own
reasoning; it never authorises an empty report.

### The confound that had to be settled first

Three threshold runs came back `no-output`. If the agent had concluded "nothing to file" and
written no file, the harness would have excluded exactly this arm's successes and inflated its
score. All three record `timedOut: true` at the 300-second limit, so the exclusion is correct
and 0.571 is unbiased — conservative, if anything, since a timeout is not a clean case.

Recorded because the failure would have been invisible: an arm that looks good partly because
its best runs were discarded reads identically to an arm that is good.

### What follows

## Python Run 1 is burned — 2026-10-14, deliberately

The fixes are to be general (cookie configuration, open-redirect method attribution, SSRF

authorisation miss), each with its own true-positive and near-miss tests, developed against
`corpus-python`, the Python families of `benchmark/corpus`, and this corpus.

again.** It measures what `corpus-python` measures: whether the engine still does what it

### What was fixed against it, as development data — 2026-10-14

Fixed at `e5ed9ad`, each with a true positive and a near miss in
`packages/scan-python/test/precision.test.mjs`. Every fix is a general mechanism, not a
case match:

* **Cookie configuration (both misses).** The cookie name was a module constant
  (`SESSION_COOKIE = "portal_session"`), which the rule did not resolve, so neither call
  was considered at all. Flags passed through `**mapping` are now read when the mapping
  is a literal the project binds; an unreadable mapping claims nothing.
* **Wrong method on a multi-method view.** A `methods=["GET", "POST"]` view is one route
  per method, and every finding was given the first. A finding now belongs to the method
  that reaches its line (`request.method` guards, `validate_on_submit()`, early exits),
  and a sink reached only by submitted data is not attributed to a GET. This was the
  open-redirect case found at the right line, and the Flask cookie case once its name
  resolved.
* **Open redirect through the session.** The FastAPI case stores `return_to` in
  `request.session` in one route and redirects to it in another. Session values are now
  followed between routes by key, and count as attacker data only when some route stored
  request data under that key without making it safe for the sink.
* **Object-level authorisation.** The handler named `current_user` only inside
  `record_event(..., actor_id=current_user.id)`, which the rule took for an ownership
  check. Audit, log and notification calls, and stamping the caller on the record, no
  longer count.
* **SSRF allow-lists (two findings on correct code).** `parts.hostname not in
  PARTNER_HOSTS` cleaned the attribute, not the URL it was parsed from. A parsed host
  tested against a fixed set or host now pins the URL; `endswith` counts only from a
  label boundary and `startswith` only when the prefix closes the authority, so the
  substring forms stay reported.
* **Bound SQL (one finding on correct code).** `where, params = _where_clause(args)`
  gave `where` the taint of `params`. Tuple positions are now kept.
* **Same-host redirect check (one finding on correct code).** `_is_same_site()` was
  recognised by name only. A project predicate is now read by what it returns: a parsed
  host compared with this request's host, a fixed host or an allow-list.

Found while probing the same classes, and fixed in the same commit: a component test such
as `urlparse(url).scheme != "https"` cleaned the whole URL for every sink (a true
positive lost, not a false one); a validator that refuses unless the host is allowed now
protects the caller's argument after the call; refusing private addresses the host
resolved to counts as an SSRF guard; a conditional expression is read arm by arm; a
FastAPI route with `response_class=HTMLResponse` serves its string as HTML; and calls on a
module-level instance of a project class reach its methods.

### What it establishes, and its caveats

Against Python Run 1 (0.821 recall, 0.852 precision, 4 of 30 safe flagged) the point
estimates moved the right way for precision and the wrong way for recall, but on about 30
cases a side the 95% intervals overlap almost completely ([0.602, 0.886] here against
[0.644, 0.921] then), so no difference between the two runs is measurable. Read it as
one more blind sample of the same engine scope, not as a trend.

The caveats travel with the figure:

* **Scope.** Its thirteen classes are the Python engine's own, so it measures coverage of
  that scope on unseen code, not coverage of Python applications in general.
* **The author knew where the engine was weak.** As the author's section above
  discloses, the author read Python Run 1, which names the classes and guard shapes the
  engine then missed (cookie flags, open redirects, host allow-lists, same-host checks).
  That can only make this corpus harder for exactly those classes, and they are the
  classes the fixes above addressed.
* **The developer did not see the ids.** Unlike Run 1, the developer of the fixes never
  saw this corpus's ids or hand-back before scoring; the ids are opaque in any case.

### Status

**Scored once. Not tuned against.** `holdout-python-2` is now the Python held-out figure
quoted on `/benchmarks`, in ADR 020 and on the Python docs page, replacing Run 1. Fixing
any of the nine items above burns it, the same way Run 1 was burned, and a third Python
holdout would then be needed before a Python generalisation figure is quoted again.

### What was fixed against it, as development data — 2026-10-14

Fixed at `04ccbb3`, each with a true positive and a near miss in
`packages/scan-python/test/precision-2.test.mjs`. Every fix is a mechanism, not a case
match; the case each one was found through is named so the reading can be checked.

* **Background tasks** (`hp2-fastapi-02`, command injection). The shell command was built
  in a function handed to `BackgroundTasks.add_task(render_variant, source, target, req)`,
  and functions passed to a scheduler were not followed. A project function handed to
  `add_task`, `submit`, `to_thread`, `run_sync`, `run_in_threadpool`, `run_in_executor`,
  `start_soon`, `spawn`, `enqueue`, `Thread(target=, args=)`, `Process(...)`,
  `task.delay(...)` or `task.apply_async(args=...)` is now applied with the arguments it
  will run with.
* **Object-level authorisation in a service** (`hp2-fastapi-21`). The handler passed the
  caller to `service.rename(project_id, name, user)`, which the rule took for an
  ownership check, and the lookup itself sat in the service, where lookups were not
  observed. Lookups in project helpers are now recorded against the parameter that
  chose the record and attributed to the route that passes it a request identifier; a
  subject handed to a helper counts only if the helper uses it to decide (stamping it on
  an audit column does not).
* **Presence check taken for ownership** (`hp2-flask-13`). `if current_user.patient_id is
  None: abort(403)` mentions the subject, but only to ask whether the caller is a patient
  at all. A test whose every reference to the subject is a presence or sign-in check is no
  longer ownership evidence; a privileged-role test (`role`, `is_admin`, …) still is.
* **Scoped query built by a helper** (`hp2-flask-04`, finding on correct code).
  `_visible_results().filter_by(id=result_id)` was scoped to the caller inside
  `_visible_results`, which the rule did not read. A helper that builds the query a lookup
  runs on, receives the subject, or contains the lookup is now read for ownership, with
  Flask's signed-in user as a subject it can read itself.
* **Stored cross-site scripting** (`hp2-fastapi-22`, `hp2-flask-14`). Both stored request
  data in a record field (`Note(body_html=markdown(body.text))`, `Comment(body=form_body)`)
  and rendered it raw in another route (`{{ note.body_html | safe }}` in a template
  compiled with `env.from_string`, `Markup(...)` after a regex edit). Values stored in a
  database were not followed. A value a route writes to a persisted record's field (ORM
  constructor keywords, or an attribute assigned on a loaded record or the signed-in user,
  in a function that commits or saves) is now followed, by field name, to unescaped markup
  and template source that read the field back, and resolved after every route is
  analysed, as session values are. Stored data reaching any other sink is not reported.
  Templates compiled in code, `get_template` and FastAPI `TemplateResponse` are read for
  `| safe` on context attributes and loop variables; markdown renderers carry raw HTML;
  a compiled regex's `.sub()` returns its subject.
* **Wrong method** (`hp2-flask-29`, template injection found under `POST`). The signature
  was assigned to `current_user` in the POST branch and rendered after it on every method.
  An attribute assigned on one branch now keeps its earlier, stored value on the other, so
  the GET that renders a stored signature carries it and the finding belongs to GET.
* **Missing authentication** (`hp2-fastapi-31`). `user = await session.get(User, user_id);
  if user is None: raise HTTPException(404)` was read as an in-body identity check because
  the record is called `user`. A test on a record the handler loaded, or on a parameter the
  request chose, is no longer identity evidence.
* **SSRF host allow-list** (`hp2-fastapi-06`, finding on correct code). The host was
  `(parts.hostname or "").lower()`, and `x or ""` dropped what was known about `x`. A
  literal fallback now keeps it. Found while probing the same mechanism, and fixed in the
  same commit because it lost true positives: a check on a URL's scheme or port through a
  local (`scheme = parts.scheme; if scheme not in (...)`) cleaned the whole URL. Only the
  authority of a parsed URL now speaks for its destination, and only for SSRF and
  redirects.

Found while checking the fixes for new false positives, and fixed in the same commit: SQL
that aggregates (`GROUP BY`, `SELECT COUNT(...)`) or filters a joined table's code is not a
record lookup (a revenue report on `hp2-fastapi-03` became a finding once helper lookups
were observed); and `SESSION_COOKIE_SECURE = False` in a development or test configuration
class is no longer reported, as `DEBUG = True` there already was not.
